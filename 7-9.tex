\begin{abstract}
The deployment of generative models calls for automated red-teaming methods that discover failures beyond manually authored test cases. This survey examines systems that generate, execute, and evaluate adversarial or safety-relevant interactions with generative models and model-based applications. We cover large language models, vision-language models, text-to-image and text-to-video systems, retrieval-augmented applications, and tool-using agents. We organize the literature around a closed-loop pipeline connecting risk objectives, test-case generation, interaction and execution, outcome judgment, failure triage, and mitigation. This framework groups red-teaming strategies by search space, optimization signal, access assumptions, interaction horizon, and modality. We compare evaluation metrics, benchmarks, automated judges, human-in-the-loop protocols, and reporting practices, focusing on attack success, harm severity, coverage, transferability, cost, and over-refusal. We identify open problems in adaptive coverage, reliable evaluation, stateful long-horizon testing, cross-modal and multilingual transfer, durable remediation, and governed disclosure. The survey provides a common vocabulary for comparing these approaches and a practical roadmap for scalable automated red-teaming evaluations grounded in evidence.



\end{abstract}
\keywords{automated red teaming; generative models; large language models; vision-language models; text-to-image generation; AI safety; adversarial evaluation; jailbreaks}

\subsection{Learning from Red-Team Failures}

Early automated red teaming focused on scalable failure discovery and characterization~\cite{ganguli2022redteaming,perez2022redteaming}. Subsequent work uses red-team outputs as training signals. Verified failure traces provide adversarial prompts for safe demonstrations, negative examples for preference optimization, hazardous concepts for unlearning, and attack sets that can be updated as targets change~\cite{bianchi2024safetytuned,ge2024mart,lee2025diverseattacks,zhao2025diverct,mazeika2024harmbench,wu2025trident}. These uses connect failure discovery to model development through defensive alignment.

A direct use of red-team findings is to pair adversarial instructions with safe responses and fine-tune the target model on the resulting demonstrations. MART~\cite{ge2024mart} and TRIDENT~\cite{wu2025trident}, for example, generate adversarial prompts and corresponding safe completions for supervised fine-tuning, giving the model examples of safe behavior on inputs it previously failed. Unsafe completions also supply negative examples for preference modeling. An unsafe response $y_{\text{harm}}$ paired with an aligned alternative $y_{\text{safe}}$ yields a preference pair for Direct Preference Optimization (DPO)~\cite{rafailov2023directpreference} or Safe RLHF~\cite{dai2024saferlhf,ji2023beavertails}. The negative example thus comes from an observed vulnerability. Representation editing and unlearning methods also use activations associated with failures to remove hazardous domain knowledge while preserving general task performance~\cite{yao2024unlearning}.

Safety tuning depends on training data that cover distinct attack vectors while preserving benign utility. Lee et~al.~\cite{lee2025diverseattacks} train red-team policies to produce prompts with varied behavioral profiles and use the examples for defensive tuning. DiveR-CT~\cite{zhao2025diverct} relaxes generation constraints to broaden the attack space, while TRIDENT~\cite{wu2025trident} organizes data generation across lexical variations, malicious intent categories, and jailbreak tactics. Contrastive evaluation sets help distinguish harmful intent from sensitive vocabulary: indiscriminately penalizing sensitive keywords can cause models to reject benign requests. XSTest~\cite{rottger2024xstest} and OR-Bench~\cite{cui2025orbench} support this calibration of defensive data and refusal behavior~\cite{pan2025overrefusal}.

Fine-tuning changes model behavior and the vulnerabilities that red teams need to find. MART~\cite{ge2024mart} alternates attack generation with safety fine-tuning over multiple rounds, directing new attacks at the latest model state. R2D2~\cite{mazeika2024harmbench} maintains adversarial test cases that are continuously optimized as the model updates. Tests on held-out harm categories and attacks transferred across models can assess whether these updates generalize to unseen strategies or depend on familiar prompt templates.

Runtime defenses complement these weight updates by inspecting prompts, guiding decoding, and moderating outputs as deployed systems process untrusted inputs and changing context. Section~7.2 examines these interventions.

Input guards examine or sanitize prompts and retrieved context before inference. Llama Guard~\cite{inan2023llamaguard}, ShieldGemma~\cite{zeng2024shieldgemma}, and WildGuard~\cite{han2024wildguard} assess prompts and outputs against safety taxonomies to detect harmful requests, jailbreak attempts, and inappropriate content. For indirect prompt injection, BIPIA~\cite{yi2025bipia} uses boundary-aware representations and explicit reminders, while Spotlighting~\cite{hines2024spotlighting} encodes provenance to separate untrusted external data from system instructions. Other defenses address sensitivity to adversarial changes in prompts. SmoothLLM~\cite{robey2023smoothllm} applies randomized character- and token-level perturbations and aggregates predictions across copies; Erase-and-Check~\cite{kumar2023erasecheck} evaluates token subsequences to certify robustness against adversarial token insertions. SemanticSmooth~\cite{ji2024semanticsmoothing} extends randomized smoothing to meaning-preserving paraphrases. Input defenses thus cover intent filtering, context boundaries, and certified robustness.

Decoding interventions steer generation as it proceeds. SafeDecoding~\cite{xu2024safedecoding} adjusts token probability distributions using safety-guided directional vectors, while Reasoning-to-Defend~\cite{zhu2025reasoningtodefend} inserts a safety-deliberation step before the final response. Jailbreak Antidote~\cite{shen2025jailbreakantidote} steers hidden representations at inference time to suppress harmful concept activation. These methods retain the model parameters, with trade-offs in computation, response latency, and general utility.

Output moderation checks, filters, or rewrites candidate responses before they reach the user. LLM Self Defense~\cite{phute2023llmselfdefense} asks the model to check its generated text for safety violations, while Backtranslation~\cite{wang2024backtranslation} infers user intent from the response to check compliance. AutoDefense~\cite{zeng2024autodefense} distributes screening across specialized defender agents. AutoJailbreak~\cite{lu2024autojailbreak} provides a modular framework for analyzing dependencies among attack, defense, and evaluation pipelines, showing how input and output defenses can work together. The verification model determines the reliability of this screening. For systems that execute tools during generation, checks must also precede execution to prevent unsafe external actions.

Tool execution, persistent memory, and external side effects require controls at the system level. Section~7.3 examines information-flow boundaries, capability-based permissions, action validation, execution containment, and transaction rollback.

\subsection{System-Level Protection Beyond Model Alignment}

Applications that connect LLMs to tools, memory, APIs, and autonomous workflows extend the security boundary beyond the model. Research on indirect prompt injection, tool use, agent memory, and agent security benchmarks shows that attackers can redirect execution through user inputs, instructions in retrieved data, poisoned memory, and compromised control paths~\cite{perez2022promptinject,abdelnabi2023indirect,debenedetti2024agentdojo,chen2024agentpoison,zhang2025asb}. Downstream fine-tuning can also weaken safeguards in open-weight models~\cite{qi2023finetuningalignedlanguagemodels,yang2023shadowalignment}. System-level controls address instruction integrity, authorization, and persistent state by regulating information flow, restricting execution privileges, and containing the effects of unsafe actions.

Table~\ref{tab:system_protection_capabilities} groups defenses by where they act in the architecture. Most intervene before execution. Cordon~\cite{chen2026cordon}, SafeHarness~\cite{lin2026safeharness}, and AIR~\cite{xiao2026air} extend protection to containment and recovery through transactional rollback, adaptive service degradation, or incident remediation. These designs expand the available controls from information-flow separation and authorization to action validation, execution containment, and state recovery.

Information-flow control separates trusted instructions from external content that could redirect the task or gain execution authority. Perez and Ribeiro~\cite{perez2022promptinject} describe goal hijacking and system prompt exfiltration through prompt injection. Greshake et~al.~\cite{abdelnabi2023indirect} formalize indirect prompt injection in applications, showing that payloads in web pages or emails can hijack an agent before tool invocation or private data retrieval. AgentPoison, by Chen et~al.~\cite{chen2024agentpoison}, shows that corrupting long-term memory or a knowledge base can affect future trajectories. These attacks target both the context assembled for the current task and state retained across sessions. StruQ~\cite{chen2025struq} separates instructions and data structurally at the query interface. Wu et~al.~\cite{wu2024fsecure} formulate indirect prompt injection defense as information-flow control in the $f$-secure architecture. CaMeL~\cite{debenedetti2025camel} separates trusted control flow from untrusted inputs during execution and enforces capability-based access control on their interactions. IPIGuard~\cite{an-etal-2025-ipiguard} fixes a tool-dependency graph before the agent reads external data, preventing injected instructions from changing the planned execution structure. System architectures should track provenance and trust across retrieval, memory, planning, and tool use, and restrict the authority of untrusted content.

Authorization and action validation place application-level checks between a model proposal and its execution. Progent~\cite{shi2025progent} provides programmable privilege policies, while MiniScope~\cite{zhu2025miniscope} enforces least privilege across tool calls. Task Shield~\cite{jia2025taskshield} checks whether proposed tool actions follow the user's original task. AuthBench~\cite{do2026leastprivilege} finds that coding agents often request redundant or sensitive privileges, including when they use extended reasoning. An external reference monitor can assess proposed operations against user constraints, granted capabilities, and system state before authorizing execution.

Runtime monitoring checks actions in the context of the full execution history. Relevant evidence includes tool arguments, execution outputs, prior actions, active privileges, and changes in the environment. ToolSafe~\cite{mou2026toolsafe} checks tool calls against interaction history and returns guardrail feedback before dispatch. MELON~\cite{pmlr-v267-zhu25z} reruns trajectories with the user prompt masked; similar behavior across the original and masked runs is evidence that injected instructions are driving execution. GuardAgent~\cite{pmlr-v267-xiang25a} converts natural-language safety specifications into executable verification code, while ShieldAgent~\cite{pmlr-v267-chen25ae} checks action trajectories and safety plans against formal policies. These methods support checks of individual calls, historical traces, and formal specifications, generally intervening before an unsafe side effect occurs.

Containment and recovery address changes to the environment and the effects of unsafe actions, including effects that cannot be reversed. IsolateGPT~\cite{wu2025isolategpt} uses sandboxes to separate untrusted application components from the wider environment. Cordon~\cite{chen2026cordon} provides task-scoped transactions: it buffers internal updates in shadow memory, stages external actions, and validates the full execution atomically before commit, allowing abort or rollback on a policy violation. SafeHarness~\cite{lin2026safeharness} combines runtime state validation with automated rollback and adaptive service degradation. AIR~\cite{xiao2026air} combines contextual incident detection with containment, environment recovery, and automated rule synthesis. AgentDojo~\cite{debenedetti2024agentdojo}, ASB~\cite{zhang2025asb}, and ToolEmu~\cite{ruan2024toolemu} provide benchmark environments for testing such controls; their role is evaluation, while the controls themselves operate in deployed systems. Recovery and containment remain less studied than preventive filtering, making reversible execution and recovery behavior useful targets for further system design and evaluation.

\subsection{Continuous Testing After Remediation}

Safety evidence applies to the model weights, software dependencies, and runtime configuration used in the evaluation. Fine-tuning can weaken alignment even with benign adaptation data~\cite{qi2023finetuningalignedlanguagemodels,peng2026cwac}, and the extent of this change varies across architectures and evaluation protocols~\cite{khan2026safetydrift}. Prompt formatting can also affect refusal behavior~\cite{lyu2024keepingaligned}. Continuous red teaming preserves historical failures for regression testing and searches for new failures as the target changes.

Retained failures need provenance records that allow others to reproduce them. Drawing on vulnerability bounty programs, McGregor~\cite{mcgregor2025toerr} describes structured review workflows and audit artifacts for validating flaws. Paeth et~al.~\cite{paeth2025lessons} show how structured incident databases support longitudinal analysis and retrospective audits when root causes or broader impacts are unclear. FLARE-AI~\cite{longpre2026flareai} specifies system metadata, deterministic reproduction traces, and empirical evidence as reporting dimensions, using machine-readable schemas for triage and coordination across teams. A reusable failure record links the attack trace, exact target version, observed safety failure, and environmental configuration needed for deterministic replay.

Tracking safety drift requires evaluating successive model versions under recorded conditions. Qi et~al.~\cite{qi2023finetuningalignedlanguagemodels} show that fine-tuning on benign data can compromise safeguards. Lyu et~al.~\cite{lyu2024keepingaligned} show that tuning and inference templates affect alignment retention, making prompt wrappers a confounding factor in comparisons over time. Across more than one hundred model variants, Khan et~al.~\cite{khan2026safetydrift} find heterogeneous safety drift: gains on one benchmark often coincide with regressions on another. Peng et~al.~\cite{peng2026cwac} show that benign updates erode learned refusal boundaries and motivate explicit constraints in weight and activation space during adaptation. Regression testing across versions can measure these changes and establish which safety properties persist.

Regression replay and renewed discovery test complementary aspects of safety across deployment cycles. EvoJail~\cite{tang2026evojail} adapts attack generation to updated targets, while AutoRedTeamer~\cite{zhou2025autoredteamer} adds emerging attack strategies to a growing test suite. Jailbreak Distillation~\cite{zhang2025jbdistill} turns candidate jailbreaks into modular, maintainable benchmarks, and AgenticEval~\cite{wang2026agenticeval} develops self-updating evaluations for agentic systems. A continuous workflow combines replay of archived vulnerabilities with exploratory testing of the updated system. Deterministic execution harnesses, immutable audit logs, and reusable evaluation workflows support this combination across changes in models and environments.

An evaluation harness makes a red-teaming strategy executable by coordinating target access, attacks, judgments, trace recording, and replay. Target adapters connect to model APIs or application endpoints through a common interface. Attack orchestration manages prompt selection, seeds, query budgets, and interaction schedules, while automated judges assign structured verdicts to outputs, tool calls, or final system states. Execution traces preserve inputs, outputs, runtime parameters, software versions, and intermediate scores. Replay then reruns cases under the original conditions or against updated targets, judges, and environments to verify findings and detect regressions. In Table~\ref{tab:redteam_harnesses}, Generate and Adaptive describe test synthesis and search; Judge and Multimodal describe scoring interfaces and interaction modalities; Record and Replay describe evidence preservation and reuse. Judge support indicates that a scoring interface is available; its accuracy requires separate assessment.

Harness designs reflect different testing goals. For vulnerability scanning, garak~\cite{derczynski2024garak} pairs probes and generators with dedicated detectors in a plugin architecture. PyRIT~\cite{lopezmunoz2024pyrit} coordinates targets, orchestrators, prompt converters, and scorers in reusable workflows for multi-turn and multimodal testing. For application testing, promptfoo~\cite{promptfooDocs} uses declarative configurations for model providers, attack plugins, and automated assertions. Inspect AI~\cite{ukaisi2024inspect} combines model interfaces, tools, and containerized sandboxes with detailed logs for auditing and re-scoring. A single-turn campaign may need prompt probes alone; testing tool-using agents also requires records of multi-step state transitions in external environments. In each case, the harness defines the experimental boundary and records the provenance needed to verify safety claims.

Attack-generation systems such as GPTFuzzer~\cite{yu2023gptfuzzer}, APRT~\cite{jiang2024aprt}, AutoDAN~\cite{liu2024autodan}, and TAP~\cite{mehrotra2024tap} synthesize adversarial prompts and optimize search. Table~\ref{tab:redteam_harnesses} classifies them as workload generators. Evaluation suites and benchmark environments fix parts of the test protocol for controlled comparison. HarmBench~\cite{mazeika2024harmbench} and JailbreakBench~\cite{chao2024jailbreakbench} specify harm categories, baseline attacks, and automated evaluation routines. AgentDojo~\cite{debenedetti2024agentdojo} supplies a simulated environment for testing prompt injection against tool-using agents, while MM-SafetyBench~\cite{liu2024mmsafetybench} supports standardized multimodal safety testing. Benchmarks supply inputs, threat models, and evaluation criteria; harnesses run, record, and replay the tests.

Static suites provide stable comparisons through fixed cases and scoring rubrics. Renewable workloads extend this coverage as models, defenses, and attacks change. h4rm3l~\cite{doumbouya2025h4rm3l} represents jailbreaks as composable syntactic and semantic transformations, generating attacks that expose gaps in static datasets. Jailbreak Distillation~\cite{zhang2025jbdistill} turns varied failure traces into modular benchmarks that can be updated. Harnesses preserve the configurations and traces needed to run both stable baselines and renewed workloads over time. Human judgment determines which deployment risks these workloads should address and how to interpret culturally ambiguous outputs.

\subsection{Human Guidance and Automation in Red Teaming}

Human guidance defines the operational standard for a red-teaming campaign: the risks in scope, system boundaries, harmful behaviors or invalid actions, and evidence needed to confirm a failure. These choices shape both the vulnerabilities a campaign can find and the interpretation of its results. STAR~\cite{weidinger-etal-2024-star} structures human involvement through parameterized red-teamer instructions, demographic matching between annotators and harm topics, and rules for resolving disagreements. Alvarado Garcia et al.~\cite{alvaradogarcia2026sociotechnical} show that practitioners' choices about risk taxonomies, deployment scenarios, dataset generation, and rubrics determine which populations and cultural contexts benchmarks represent.

Deployment contexts also inform revisions to the standard. Adversarial Nibbler~\cite{quaye2024adversarialnibbler} uses crowdsourced exploration to collect implicit adversarial prompts and find text-to-image failures that automated pipelines often miss. Going PLACES~\cite{rastogi2026goingplaces} works with local communities to include regional cultural and linguistic norms in evaluation cases. These efforts update the risk register with previously unmodeled harms, overlooked interfaces, and failures that require context beyond isolated text outputs. DICES~\cite{NEURIPS2023_a74b697b} and D3CODE~\cite{mostafazadeh-davani-etal-2024-d3code} document widespread demographic and cultural disagreement in safety and offensiveness ratings. Such disagreement can identify evaluation rules that need human review and contextual interpretation before labels are aggregated.

Automation scales testing under these human-defined standards. AART~\cite{radharapu-etal-2023-aart} uses modular evaluation recipes to define application-specific risks and generate large adversarial test sets. Bridging the Scale Gap~\cite{quaye2026bridging} expands human-written adversarial prompts using sociolinguistic transformations learned from expert red teamers. Harnesses execute the expanded suites and retain interaction traces for comparison and replay~\cite{derczynski2024garak,lopezmunoz2024pyrit,ukaisi2024inspect,promptfooDocs}. Automated judges screen responses according to the specified rubric, observable context, and decision threshold. Human audit and adjudication calibrate judgments in high-stakes or ambiguous cases~\cite{souly2024strongreject,han2024wildguard,thakur2025judgingjudges,chen2025saferluckier}. Human oversight is thus part of routine operation: experts set criteria, examine boundary failures and disagreements, and update risk registers, escalation thresholds, and disclosure rules as evidence accumulates.

\subsection{Balancing Transparency and Exploitability}

Automated red teaming produces jailbreak prompts, multi-step exploit chains, attack scripts, and test cases alongside safety findings about a target. Disclosure decisions govern both access to these artifacts and the documentation needed to audit findings. Solaiman et al.~\cite{solaiman2019release} describe staged release of models and artifacts. OpenAI's analysis of external red teaming~\cite{ahmad2025externalredteaming} treats access controls and documentation standards as campaign-level governance decisions. In offensive cybersecurity, Fang et al.~\cite{fang2024llmagentsautonomouslyhack} withhold full prompts and step-by-step reproduction instructions from the public while granting qualified researchers access on request.

Vulnerability reporting and coordination across organizations support verification, remediation, and publication while managing security risks. Cattell et al.~\cite{cattell2024coordinatedflaw} place independent verification and formal review within coordinated flaw disclosure. Householder et al.~\cite{householder2024lessons} describe a disclosure lifecycle covering discovery, validation, coordinated remediation, and public release. Public summaries, such as those in the GPT-4 system card~\cite{openai2023gpt4systemcard}, communicate findings without exposing actionable exploits. These choices can be documented for each artifact through sensitivity assessments, access tiers, and release decisions. A general framework for making such decisions remains a research question.

Reporting makes findings auditable alongside the controls governing artifact access. A report should specify the threat model and target configuration, including versions, dependencies, and assumed attacker access. Validation, developer notification, mitigation, and publication timelines document how the finding was handled. McGregor et al.~\cite{mcgregor2025toerr} describe review workflows and supporting artifacts for bug-bounty reports. Paeth et al.~\cite{paeth2025lessons} show how structured incident databases support longitudinal search and analysis, while FLARE-AI~\cite{longpre2026flareai} provides a machine-readable schema for coordinated reporting. These practices identify information to preserve and provide a basis for a common automated red-teaming reporting standard, which remains to be established.

\section{Open Problems and Future Directions}
\label{sec:agenda}

Automated red teaming connects risk identification, failure discovery under realistic configurations, validation of observed failures, and assessment of defenses that preserve benign performance. Earlier surveys organize the field around operational pipelines or attack taxonomies and search strategies~\cite{purpura-etal-2025-building,Lin_2025}. This survey connects these perspectives through a closed loop. Its research agenda addresses adaptive coverage, reliable evaluation, stateful long-horizon testing, cross-modal and multilingual transfer, durable remediation, and governed disclosure. Figure~\ref{fig:section9_research_map} shows how these six directions connect discovery to evidence that can guide subsequent testing and remediation.

\subsection{Adaptive Risk Coverage Beyond Prompt Counts}
\label{sec:agenda_coverage}

Risk coverage depends on the failure mechanisms a test set reaches. Automated methods can generate far more cases than manual red teams, yet a large collection may consist mostly of rephrasings that exploit the same weakness. A smaller set may reveal distinct mechanisms, such as instruction hijacking through retrieved context, unauthorized tool calls, or persistent memory poisoning. Static benchmarks support controlled comparisons within predefined categories~\cite{mazeika2024harmbench,chao2024jailbreakbench}. Coverage metrics should therefore distinguish new failure mechanisms from lexical variation, giving prompt, attempt, and jailbreak counts a clearer interpretation.

A risk register maintained during search can link each confirmed failure to its prompt, outcome, category, system boundary, interaction context, and reproduction steps. Clustering and novelty metrics can then be assessed by whether they separate distinct root causes. Quality-diversity search and diversity-oriented red teaming offer starting points~\cite{zhao2025diverct,li2024rtpe,jiang2024aprt,wu2025trident,zhou2025autoredteamer}. The open question is how to determine whether a new case exposes a distinct mechanism or repeats a known one in different words.

Coverage also depends on who defines the risk space. End users, domain experts, and community members frequently identify harms and deployment contexts absent from fixed safety taxonomies~\cite{weidinger-etal-2024-star,quaye2024adversarialnibbler,rastogi2026goingplaces}. Participatory red teaming brings these perspectives into test design. When expanding human findings, automated tools need to preserve the context that made each finding meaningful~\cite{weidinger-etal-2024-star,quaye2026bridging}. Evaluations should report which risks were tested and how those risks were defined. This record establishes the scope of the coverage claim.

\subsection{Decision-Grade Evaluation and Trustworthy Judges}
\label{sec:agenda_judges}

An attack success rate depends on the evaluator, rubric, and decision threshold used to calculate it. Classifiers, heuristic rules, and LLM judges can assign conflicting labels to the same response. Disagreements with human annotators are common in ambiguous, conversational, or culturally dependent settings~\cite{souly2024strongreject,han2024wildguard,inan2023llamaguard,zheng2023mtbench,chen2024humansjudge,thakur2025judgingjudges,chen2025saferluckier,eiras2025knowthyjudge,NEURIPS2023_a74b697b,mostafazadeh-davani-etal-2024-d3code}. Adversarial search can also exploit the judge, producing outputs that fool the evaluator without exposing a system failure~\cite{raina2024robustjudge,tong2025badjudge,shi2024optimization}. Judge calibration and resistance to such attacks determine how reliably reported failures support a safety claim.

The evaluation protocol itself needs testing. Studies should define the failure criterion, whether harmful text, unauthorized actions, privacy leaks, policy violations, or task disruption. They should record the evidence visible to the judge, its version, prompt or rubric, and decision threshold. Targeted human review can calibrate automated judgments on high-stakes and ambiguous cases. Reporting where judges and human raters disagree, alongside summary agreement scores, makes the protocol's behavior easier to assess.

In agentic and multimodal systems, evaluation also needs to attribute failures to components. An intermediate text response may appear safe while the surrounding trajectory leads to an unsafe tool call. The final outcome alone may not reveal whether the cause lies in the model, a tool, a permission setting, or the environment. Linking failure criteria to the component under test supports more precise conclusions and identifies where additional evidence is needed.

\subsection{Stateful and Long-Horizon System Testing}
\label{sec:agenda_stateful}

Interaction trajectories are the unit of testing for applications that retrieve documents, retain memory, call tools, or act in changing environments. Most evaluations use isolated prompt-response pairs. In a multi-step application, however, an apparently harmless early step can lead to an unsafe outcome later. The failure may be an unauthorized action or an irreversible external effect. Agent benchmarks have begun to capture indirect prompt injection, tool-based privilege escalation, and multi-step task failures~\cite{debenedetti2024agentdojo,zhan2024injecagent,ruan2024toolemu,chen2024agentpoison,zou2025poisonedrag,wang2025webinject}.

The next step is to evaluate trajectories as structured objects. A test record should capture the initial task, retrieved context, memory state, active permissions, tool calls, intermediate decisions, and final outcomes. This detail makes it possible to determine how a defense works: whether it blocks an unsafe action, changes how the model interprets untrusted content, or simply causes the task to fail early. It also supports evaluations of containment and recovery, which require evidence beyond a final text label.

Long interactions create failure modes through accumulated errors. Tool-output parsing errors, conversational state drift, and nondeterministic environment feedback can combine to move an agent into unauthorized states. Simulated environments with deterministic state checkpoints, reversible mock actions, and detailed trajectory attribution can help test these workflows. Tracing the full interaction makes it possible to distinguish model reasoning errors, ambiguous tool interfaces, and failures in system orchestration.

\subsection{Cross-Modal, Multilingual, and Systemic Transfer}
\label{sec:agenda_transfer}

Attack and defense transfer varies across modalities and languages. Text-based English benchmarks cover many prompt injection and jailbreak behaviors, while multimodal systems add visual prompt injection, typographic attacks, and cross-modal embedding conflicts~\cite{liu2024mmsafetybench,ying2024safebench,liu2025videosafetybench}. Safeguards can also be less effective in low-resource languages, dialects, and code-switching settings than in English~\cite{deng2024multilingual,yong2023lowresource,rastogi2026goingplaces}. Transfer evaluations should test vision, audio, video, and varied linguistic contexts to establish where failures and defenses carry over.

A system-level transfer evaluation varies the attack and its deployment configuration. We define the evaluation space as $\mathcal{S} = \mathcal{A} \times \mathcal{M} \times \mathcal{D} \times \mathcal{E}$, with attack representations $a \in \mathcal{A}$, target foundation models $m \in \mathcal{M}$, defense alignment strategies $d \in \mathcal{D}$, and host deployment runtimes $e \in \mathcal{E}$. Empirical transferability $\mathcal{T}(a, m, d, e) \in [0, 1]$ measures adversarial success in a given configuration. An attack may transfer across base models ($m \to m'$) yet fail under a different retrieval pipeline or system prompt ($e \to e'$). Tool-orchestration flaws may recur across base models that share the same control flow. Evaluating $\mathcal{T}$ across these four dimensions can help distinguish model vulnerabilities from host-application weaknesses~\cite{liu2023houyi,wu2025darkfunction} and locate the source of transfer more precisely than a single source-to-target rate.

This separation can guide remediation. An attack on an enterprise assistant may exploit permissive tool authorization, unvetted retrieval embeddings, or foundation-model behavior. Transfer tests across modular pipelines can help determine whether the appropriate intervention is model retraining, input sanitization, or privilege scoping. Standardized benchmarks across systems would also test whether mitigations generalize across deployment targets and runtime configurations.

\subsection{Durable Safety Improvement Under Changing Conditions}
\label{sec:agenda_remediation}

Durable remediation addresses failure mechanisms as models and evaluation conditions change. A fix may suppress known prompts while leaving the mechanism intact, reduce one harm while increasing benign over-refusal, or introduce weaknesses in other application settings. Iterative red teaming and safety fine-tuning generate new attacks for updated models, while retained failures provide regression benchmarks~\cite{zhou2025autoredteamer,zhang2025jbdistill}. Evaluations need to establish whether observed improvements reflect reduced risk or changes in the attacker, judge, or test setup.

A continuous testing framework should separate four sources of change: the target system, the attack generator, the evaluation judge, and the test protocol. A change in any one of these can alter safety scores. Updates to the target can shift safety behavior after fine-tuning~\cite{khan2026safetydrift,peng2026cwac}. New attack suites can find failures missed by older tests~\cite{doumbouya2025h4rm3l,zhang2025jbdistill}. Updated judges can reclassify past outputs~\cite{thakur2025judgingjudges,chen2025saferluckier}. Versioned test traces should therefore store enough detail to replay interactions under original conditions and rerun them under updated rules. Comparing these runs clarifies whether a failure was fixed, changed in severity, or disappeared because the evaluation protocol changed.

Remediation studies should measure practical costs alongside safety gains. They should identify the intervention point, test attack families excluded from training, and report changes in benign-task performance, latency, human review workload, and tool functionality. Confirmed failures provide permanent regression tests; continued discovery tests the updated system for additional weaknesses. Together, these evaluations track residual risk over time.

\subsection{Comparable Evidence and Governed Disclosure}
\label{sec:agenda_governance}

Shared infrastructure makes safety evidence comparable across systems and over time. Evaluation harnesses, renewable benchmarks, and structured incident reports preserve configurations, interaction traces, judgments, and environments~\cite{ukaisi2024inspect,zhang2025jbdistill,mcgregor2025toerr,paeth2025lessons,longpre2026flareai}. Reporting the threat model, system configuration, attacker access, query budget, evaluator, success criteria, and artifact release policy allows readers to assess whether differences in results reflect robustness or test setup. Access controls can support these comparisons while restricting dangerous exploit materials.

Tiered disclosure can pair reproducibility with controls on sensitive artifacts. Aggregate metrics, report schemas, and evaluation code can support open review. Reliable jailbreaks, exploit chains, and automated attack scripts may need restricted access because they can lower the barrier to misuse. Disclosure models should link artifact sensitivity to access controls and minimum reporting requirements~\cite{solaiman2019release,fang2024llmagentsautonomouslyhack,cattell2024coordinatedflaw,householder2024lessons}. Gated access and coordinated disclosure can allow independent verification while limiting the spread of actionable exploit code.

Durable, auditable evidence gives automated red teaming a basis for safety decisions. A testing system should record which risks were examined, how outcomes were judged, which components failed, how vulnerabilities were addressed, and which evidence is available for independent inspection. These records connect individual findings to subsequent evaluation and remediation.
\section{Conclusion}

This survey organizes automated red teaming as a closed-loop safety-evaluation system. It connects risk specification, test generation and search, interaction, judgment, coverage, mitigation, and responsible operational practice across generative-model targets. The resulting framework links discovered failures to reproducible evidence, targeted remediation, and continued testing.
